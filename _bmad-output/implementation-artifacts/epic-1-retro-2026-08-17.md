## Successes & Strengths

**The three-layer adversarial code review (Blind Hunter / Edge Case Hunter / Acceptance Auditor) has
a 7-for-7 hit rate on catching a real, load-bearing safety bug the story's own TDD missed.** Every
single story shipped at least one finding that would have left `trading_permitted` (or an equivalent
safety property) `True` when it shouldn't have been, and none of them were reachable by the tests as
originally written:

- **1.1:** `GateDecision.mode` was hard-coded to the branch that produced it, so a *refusal* could
  misreport `mode=REAL_MONEY` for an operator who was just trying to run paper.
- **1.3:** an unvalidated `trader_id` with no `-` panics in Rust and aborts the whole process
  (exit 134) — uncatchable by `except BaseException`, and reachable from the component tier.
- **1.4:** an unguarded third-party attribute chain (`node.kernel`, `IB_CLIENTS`, `client.accounts()`)
  could raise `AttributeError` and escape with the node still connected — the exact opposite of the
  gate's fail-closed contract, inside an AC the Acceptance Auditor had already judged satisfied.
- **1.5:** the delayed-data guard would have shut down a *healthy* session every single RTH re-open
  (IBKR republishes yesterday's last bar stamped with today's clock) — this would have made the
  phase's entire premise (multi-day unattended paper sessions) unusable from day one.
- **1.5:** paced subscription dispatch died silently after batch 2 on a real `LiveClock` — all four
  pacing tests were green because `TestClock` pops a fired timer before invoking its callback, which
  `LiveClock` does not.
- **1.6:** a flapping connection (50s down / 1s up, repeated) defeated the halt indefinitely — Edge
  Case Hunter drove 200 cycles (2.8 simulated hours of an unusable link) and `connection.halted` never
  fired, in the one story whose entire job is firing that event.
- **1.7 (salvage):** a blanket `except OSError` would have misclassified a local log-directory
  permission error as `BROKER_UNREACHABLE`, sending an operator to restart a healthy gateway.

Quinn (QA): "That's the headline finding of the whole epic for me. Our own TDD is necessary but not
sufficient for a safety-critical, long-running, low-observability system — the adversarial layer is
what's actually catching the worst bugs, every time, in the same direction: fail-open paths hiding
inside ACs already marked satisfied."

**"Verification by execution" — running live against the real Gateway or the real wheel, and
simulating extreme runs rather than trusting a dry run or the docs — repeatedly found what static
review and mocked tests could not:**
- Story 1.3's live probe run surfaced a real `asyncio` event-loop bug (`dispose()` called from inside
  a still-running coroutine) that none of the automated tests could reach, since NFR32 forbids
  automated tests from touching a real broker.
- Story 1.6 had to read the installed `nautilus-trader` 1.220.0 wheel directly to learn that an IBKR
  disconnect publishes **no** message-bus event and changes **no** public connection property — the
  natural implementation (`check_connected()`) would have been permanently wrong.
- Story 1.7's live run surfaced the 115-second additive-timeout bug (`--connect-timeout` and
  `node.build()`'s own retry budget were being spent in series, not as one bounded window) — the
  mocked component-tier double did not catch it because it doesn't model real handshake timing.
- Mutation testing (deliberately breaking the fix to confirm the test fails) was used explicitly in
  Story 1.5 to compensate for a Task-3 TDD-Red-phase skip, and caught the same class of "test that
  can't fail" issue as the `LiveClock` bug above — used honestly, with the gap disclosed rather than
  a false Red claimed.

**The team demonstrably learned and applied a lesson within the epic itself, with no prior retro to
draw from.** Story 1.3's review produced a retracted finding — a "stale test-count baseline" claim
that turned out to be comparing *passed* counts against *collected* baselines. Story 1.4 explicitly
adopted "always baseline as collected counts, taken pre-edit" specifically to not repeat that mistake
— and it didn't recur in 1.4, 1.5, 1.6, or 1.7's own testing-insight records.

Amelia (Dev): "1.1's `.env.example` friction and 1.2's stale `IBKR_CLIENT_ID=10` both got escalated
for a one-off approved write rather than quietly worked around — the hook did its job both times."

**Fail-closed was the uniform resolution to every ambiguous safety-ruling this epic, with no
exceptions.** Story 1.1's Decision 1 and 2 both kept the code as spec'd and fixed the documentation
instead of loosening a check; Story 1.6's three review decisions were all ruled "option (a), fail
closed"; Story 1.7 chose exit code `1` over inventing a nonstandard `130` rather than stretch the
documented exit-code table.

## Challenges & Growth Areas

**Live-verification coverage is real but incomplete, and that gap is more concentrated than the
"non-blocking" label on each individual deferred item suggests.** Of five live-verification
procedures (P1 through P5, one per story from 1.3 onward), only P1 got a clean pass. P3 met 2 of 3
criteria (market was closed for the third). P5 never completed the happy path at all — the paper
Gateway accepted the TCP connection but the IB API handshake never finished, even after ruling out a
stale client ID. P2 and P4 never ran — no `.env` existed in the implementation worktree in either
case. **No procedure has ever observed a full connect → stream → strategies-would-start round trip,
live, start to finish.** Individually, each story's automated coverage stands on its own (NFR32/NFR34
exist precisely so a broker isn't required to trust the story). Collectively, this is the one gap
worth being explicit about before Epic 2 starts running sessions continuously.

**A dev session dying mid-story before commit or review is a real, demonstrated risk, and nothing
currently guards against silent drift when it happens.** Story 1.7's first implementation run died on
an API drop before it reached commit or code review, leaving an uncommitted worktree. The 2026-08-15
salvage session had to re-derive and re-verify everything from that state rather than trust the
recorded "Final" numbers — and found two real, undocumented defects that had crept in after the
recorded state: an overly broad `except OSError` classification bug, and a wrong import path that
silently broke an entire component test file's collection. Neither was caught until a manual
diff-audit during salvage.

**Documentation repeatedly overstated what the code actually does, in the safety-relevant direction
(claiming *more* protection than exists), and code review caught it each time rather than the dev's
own re-read:**
- Story 1.1's Dev Notes originally claimed the gate is "an AND of three independent conditions,"
  which review found overstated — on the default bare-metal configuration it reduces to one
  condition (the port), and Layer 2 (Story 1.4) is load-bearing, not "belt-and-braces" as the
  original phrasing implied.
- Story 1.3's AC #4 (mirrored in architecture.md's AR20, now amended above) described a guard
  ordering the Nautilus API cannot expose — the code was correct; the acceptance-criterion text was
  the actual defect.
- AR41's normative log-event list (also amended above) fell behind the events Stories 1.6 and 1.7
  actually shipped, twice.

**Two structural gaps discovered mid-epic don't have a clean owner yet and were pushed forward one
epic at a time rather than resolved once:** the "zero bars ever delivered" blind spot was found from
three separate angles across three stories — 1.5 (bar lateness, not absence), 1.6 (socket-state
detects a dead link but not a dead *subscription*, per IB error 1101), 1.7 (the CLI check has no
poll loop to hang a watchdog off). All three arrive at the same conclusion: this needs a poll loop
that outlives a single command invocation, which is Epic 2's runner. That's a reasonable sequencing
call, not a mistake — but it means Epic 2 inherits three stories' worth of partial analysis on one
problem rather than one clean spec.

## Key Insights / Cross-Story Lessons

1. **A test-double that diverges from production timing/semantics is worse than no test** — proven
   twice (1.5's `TestClock` vs `LiveClock` timer-naming bug; 1.6's except-arm tests that never
   actually reached the except branch). Both were only caught because the team went looking for it,
   not because the test suite flagged it.
2. **Config-time validation beats kernel-time validation** for anything on the safety-critical path —
   1.5's review flagged that `build_bar_observer_config` validated nothing, deferring bar-type errors
   to kernel build time in a module whose entire thesis is "fail before a socket opens."
3. **Baseline test counts as *collected*, not *passed*, taken before any edit** — a Story 1.3 mistake,
   fixed once, never repeated.
4. **Case-folding asymmetry needs its rationale stated in code, correctly** — Story 1.4's first-drafted
   comment for why the paper-prefix check upper-cases but the real-money identity check does not had
   the safety direction backwards (refusal-widening vs. permit-widening); review caught and rewrote it
   so a future reader can't "fix" it into being wrong.
5. **Reading the installed library wheel, not the docs, settled five separate design questions in
   Story 1.3 alone** (TradingNodeConfig assembly doesn't touch C logging; `NautilusKernel` guards its
   own re-init; both IB clients sharing a client ID is by design, not a collision; the exec factory
   needs `account_id` passed explicitly; there's no read-only knob for an operator-run gateway) — this
   is a technique worth naming explicitly rather than leaving implicit.

## Significant Discoveries

No epic-2 **scope or acceptance-criteria** rewrite is required — Story 2.5's ACs describe an ordered
phase sequence (`gate:static → node:build → node:connect → gate:account → reconcile → warmup →
subscribe → trading`) without mandating an implementation mechanism, so nothing in `epics.md` is
factually wrong. But one finding is concrete enough to flag prominently rather than let it surface
mid-implementation:

> **`NautilusKernel.start_async()` has no hook between "engines connected" and "trader started."**
> Discovered in Story 1.4's review, restated in 1.6 and 1.7. A runner that polls
> `exec_engine.check_connected()` (the way the diagnostic probes do) observes `True` partway through
> that single coroutine and races its continuation. Epic 1 never noticed because it configures zero
> strategies — `strategy_states()` is `{}` and the ordering guard is vacuously satisfied even when
> `Trader.start()` has already run. **The moment Epic 2's runner configures a strategy, this becomes
> a live, nondeterministic bug**, not a hypothetical one. A poll-based placement of `gate:account`
> will pass in testing and fail intermittently in production depending on reconciliation timing.

This — plus `READY` being reachable after an in-process reset with no state-name distinction from
"never started" — means **Story 2.5 needs to be planned with this constraint in hand**, not discovered
during its own implementation. Recommended: drive `gate:account` from a real hook (an `on_start`-style
kernel callback, a custom `Controller`, or starting the node with zero strategies and adding them only
after the gate returns) rather than a poll loop.

## Action Items

**Process (apply starting Epic 2):**
1. Keep the three-layer adversarial review mandatory for every story — 7/7 hit rate on real,
   safety-relevant findings this epic; nothing observed suggests diminishing returns.
2. When a session dies before commit/review, the resuming session should diff the full uncommitted
   worktree against the last committed state before trusting any previously recorded numbers —
   Story 1.7's salvage found two real silent defects this way and a plain "re-run the tests" would
   have missed the import-path break (it broke *collection*, not a specific assertion).
3. For any newly-introduced load-bearing guard, apply mutation testing (deliberately break the fix,
   confirm the test fails) as a named verification step, not an ad hoc afterthought — it's what
   caught 1.5's and 1.6's worst bugs.

**Technical — Epic 2 runner / Story 2.5, concrete and evidenced (see Significant Discoveries above):**
4. Do not place `gate:account` via a poll loop against `exec_engine.check_connected()` — use a real
   Nautilus hook.
5. Track "has this trader actually started" independently of `ComponentState`, since `READY` is
   reachable after a reset and the ordering guard can't tell the two apart from the state name alone.
6. Set an explicit `LoggingConfig` and connection/disconnection/post-stop timeouts on
   `TradingNodeConfig` rather than inheriting Nautilus defaults silently.
7. Ensure `confirm_state_reestablished()`'s only production call site runs after genuine
   reconciliation completes, never immediately after observing a live socket.
8. Decide the threading confinement for anything the connection monitor or bar observer touch —
   `LiveClock` fires timer callbacks from a Rust thread, not the caller's thread.
9. Give the runner a first-bar/zero-delivery watchdog as an interim measure (Epic 4 owns the
   permanent broker-authoritative fix) — this closes the loop on three separate stories' partial
   findings on the same blind spot.
10. Apply the same `--connect-timeout`-shaped bound around `node.build()` in the runner's session
    start that Story 1.7 had to add for the CLI check.

**Non-blocking, lower priority (owner: whoever next touches the area; full list remains in
`deferred-work.md`):** the ~30 remaining deferred items not called out above, including the
`DataCatalogService` typed-settings gap, `ENV=dev/qa/prod` not propagating to nested `IBKRSettings`,
`--client-id 0` being silently swallowed, and the four Epic-3-scoped items (`docker-compose.yml`'s
`READ_ONLY_API`, `load_ids` on the exec client's instrument provider, IB error 1101's resubscription
gap, and `classify_failure`'s string-coupling to exception class names).
