## Successes & Strengths

**The clause-verification-matrix method (invented in 3.1) spread and held.** Decomposing every AC
into independently-mutated obligations, with a table mapping each obligation to the specific test
that kills it, was reused through 3.2–3.5 and is now standing practice rather than a one-off. Its
explicit thesis — *"I added a test" is not proof that an AC is guarded* — is the single most-repeated
idea across all seven stories' review sections.

**Dedupe-and-mark beat dedupe-and-drop, and the pattern reused correctly.** Story 3.3 chose to mark
duplicate/ambiguous events (`duplicate=True`, `order_qty_unknown=True`, an `over_fill` flag) rather
than silently discard them — preserving both correctness and the evidence that something unusual
happened. Story 3.5 inherited the same instinct for its aggregation logic without having to relearn
the lesson.

**Two-directional, code-derived pins became a standing CLAUDE.md rule mid-epic.** Story 3.1 found that
an exact-set pin compared against a second hand-written list only catches shrinkage, never a name
that was never added. Story 3.3 fixed this for `EMITTED_ORDER_EVENTS` by deriving the pin from the
observer's own dispatch map, and the fix was written into CLAUDE.md as a general rule — which Story
3.5 then applied correctly from the start for `EMITTED_TRADE_EVENTS`, without review having to
rediscover the problem.

**Per-story live-Gateway checks, adopted from the Epic 2 retro's AI-6, actually stuck.** Every story
from 3.2 onward gated itself on a live check rather than banking the live tier for the epic's last
day, a genuine behavior change from Epic 2's pattern (where P6 never ran and two order-path blockers
went undiscovered for two epics).

**Reviews consistently self-corrected the dev's own record rather than rubber-stamping it.** Story 3.2
had four checkable counts found wrong (test counts, line counts, an Epic 1 sweep unit confusion);
Story 3.7 caught its own mutation count off by one; Story 3.3's RED-evidence gap was closed as
"unobtainable, not satisfied" rather than fabricated after the fact. None of these changed a
conclusion, but the discipline of catching and correcting them in the open is itself a strength worth
naming.

**First live proof of the phase's central deliverable.** `p7-fill-0901` (2026-09-01) closed a
two-epic-old evidence gap — market data had been flowing for two epics while the execution path was
silently dead. P11/P12 (2026-09-21) then closed the loop with the first-ever `kill -9` with zero loss
and the first non-zero `closed trades` reading.

## Challenges & Growth Areas

**Fixture indistinctiveness defeated mutations, four separate times.** The single most recurring
failure mode of the epic: 3.2's M4 "strawman" (`ts_event == ts_init` let a real latency-anchor bug
hide); 3.3's `TestEventStubs.order_filled` deriving `trade_id` from `client_order_id`, so partial-fill
tests unknowingly modeled an event stream no venue can produce; 3.4's Hazard #6 (frozen
`client_order_id`s, non-distinctive `trade_id`s, inherited explicitly as a named lesson); 3.5 and
3.7's own instances of the same pattern. The lesson — *"when a mutation goes green, inspect the
fixture before concluding the guard is missing"* — is invoked by name in four of the seven stories.
Knowing the lesson has not stopped it from costing a review round each time.

**Self-reported counts were wrong often enough to be a pattern, not an incident.** Beyond 3.2's four
wrong counts: 3.3's "40/40 vs 43/43" triggered a review flag that was then *withdrawn* — both numbers
were correct, just different units, and the confusion traced back to language 3.2's own review
introduced. None of these changed a conclusion, but as the story itself put it: *"a record that
reports unverified numbers alongside verified ones spends the credibility of both."*

**"Zero guard-list edits" claims kept turning out false.** 3.1 claimed no new hand-maintained guard
lists while having created two (`STRATEGY_MODULES`, `LIFECYCLE_HOOKS`); 3.3 edited
`_STDLIB_AND_FIRST_PARTY` for a new `Decimal` import and only disclosed it under review pressure. The
guard-list registry in CLAUDE.md's Anti-Patterns section is meant to be the single source of truth for
"which lists must be re-checked" — it is still missing at least one list that has already tripped a
story.

**A diagnosed-but-unfixed risk pattern recurred three times without ever being fixed.**
`log.error` inside an `except` block can itself raise and escape to `os._exit(1)` — flagged against
`OrderEventObserver` (3.2), `TradeRecorder` (3.5/3.6), and the new `live_order_rejections.py` (3.7). A
fix shape (`getattr`-guarded diagnostics, or a nested try/except) has been proposed each time and
applied narrowly, but the pattern itself — a diagnostic that can crash the thing logging it — is still
live at three sites.

**Weekend/RTH timing is now a predictable cost, not a surprise, and should be budgeted as one.** 5 of
7 stories gated into `review` on live-market timing alone. This is not a defect in the work, but
repeatedly discovering it story-by-story suggests the team should plan around known market hours
rather than treat each instance as new information.

**Process debt from the Epic 2 retro (D2/D3/D4) carried through the whole epic unaddressed.** See the
follow-through section below — this is the epic's most consequential miss, because Epic 4 is
DB-and-reconciliation-heavy and inherits the same gap.

## Key Insights / Cross-Story Lessons

1. **"I added a test" is not proof that an AC is guarded.** (3.1, reused through 3.5.) The clause
   matrix exists because a single "all cases handled" test can pass while covering only some of the
   cases — proven concretely in 3.3, where a would-be single test would have passed with 5 of 6 states
   actually correct.
2. **A mutation is only as strong as the fixture's ability to tell the mutant from the original.**
   (3.2, reinvoked in 3.3/3.4/3.5/3.7.) Distinguishing test data — timestamps, trade IDs, quantities —
   is not bookkeeping, it's part of the guard.
3. **When a mutation goes green, inspect the fixture before concluding the guard is missing.**
   Validated repeatedly in practice, most concretely in 3.3's M3 (a misspelled event-name constant
   that the test's own assertion silently absorbed).
4. **An exact-set pin against hand-written constants is one-directional.** Comparing a tuple to a
   second hand-written list catches shrinkage, never an omission. Pin against the code that emits the
   set, not against a second list — now a standing CLAUDE.md rule, and correctly self-applied by 3.5.
5. **Dedupe-and-mark, not dedupe-and-drop, when a record might be evidence of something real.**
   Preserves correctness and the fact that something unusual happened — a design principle, not just a
   3.3-specific choice.
6. **On-ramp artifacts (skills, templates, scaffolding) need to be included in a defect-removal
   sweep.** 3.1's review found the project's own strategy-development skill still taught the exact
   anti-pattern the story removed from runtime code, because the prose sweep never checked `.claude/`.
7. **A self-disclosed limitation is not automatically an accepted one.** 3.1's frozenset-vanishing
   probe was disclosed as adequate by the dev; review disagreed and escalated it to a fix anyway.
   Disclosure earns credibility, not automatic sign-off.

## Epic 4 Preview & Dependencies

**Epic 4 — Stop, Restart & Resume Mid-Position** (FR32–FR39): a session survives a full process
stop/restart while holding an open position and resumes mid-position with warm indicators and
broker-confirmed state, no artificial exit. Stories 4.1–4.7, all currently `backlog`.

**Dependencies on Epic 3 being solid:** Story 4.5's mid-position resume is only as trustworthy as
3.3/3.5/3.6's order-lifecycle tracking, position aggregation, and trade persistence — all of which now
carry live proof, not just test coverage.

**Items Epic 3 discovered that are previews of exactly what Epic 4 is scoped to fix** (read as
confirmation the plan targets the right problem, not as a scope surprise):
- The stale-cache reconciliation bug live-reproduced at `p7-fill-0901` (Redis held a phantom position
  the broker didn't have because nothing touches the cache at startup) → Story 4.2.
- The IB adapter double-counting a session's own fresh fill against its own position poll, producing a
  spurious phantom round trip on every entry (found in P11/P12) → Story 4.3. Not a correctness bug
  today (3.6's `trade.persist_skipped reason=reconciliation_owned` filter already excludes it from the
  trades table), but a durable reading gotcha worth Story 4.3 knowing about up front.
- The IB adapter conflating "not open" with "cancelled" on `generate_order_status_report`, which can
  mask a filled-while-disconnected order as cancelled (found in 3.4) → Story 4.3.
- The pre-submit reclaim window: `owner_epoch` (3.6) fences the trade-write instant but not order
  submission itself — an incumbent can still submit during the ~90s heartbeat detection window →
  Story 4.3.

**No significant-discovery alert.** Nothing found in Epic 3 requires Epic 4's plan to be rewritten;
the findings above slot into stories Epic 4 already has scoped for them.

**One item worth an explicit sanity check before or during Story 4.2:** `confirm_state_reestablished`
has had **zero production callers** through the entirety of Epic 3, by design (Story 3.2's "AC #4
trap" — every story's `trading_permitted` reasoning has been built around that flag staying `False`
for the life of a session). Epic 4 is the first place this call path goes live. Worth confirming
nothing upstream silently assumed permanent dormancy rather than "dormant until Epic 4."

## Decisions Ruled at This Retrospective

Three rulings were explicitly punted here by name — all now closed:

- **D-G** (Story 3.7): AR29's `--json` live-status output was missing a `degraded_because` key
  explaining *why* a strategy degraded. **RULED: add the key.** Operators scripting against `--json`
  currently can't see why a strategy degraded without reading the human-readable view.
- **D-I** (Story 3.3): venue rejection/reason text is logged verbatim per AC #3, but NFR26's anti-field
  redaction scan only checks key names, not values — so IBKR text could carry something sensitive
  through a value the scan can't see. **RULED: keep logging verbatim; document the gap as an accepted
  limit.** Venue text is diagnostic value in a paper-trading system with no real money at risk;
  value-level scanning is not worth building now.
- **IB-error-code-outside-`ORDER_REJECTION_CODES` delay** (Story 3.7, routed to "Story 4.3 or the
  Epic 3 retrospective, whichever Allay rules"): an error code outside the known rejection set
  produces no structured event at all — the operator sees nothing until Story 3.4's in-flight sweep
  resolves it as `OrderRejected(reason="UNKNOWN")`, potentially minutes later, with the real reason
  living only in an adapter log line. **RULED: Story 4.3.** Bundled with the other IB-adapter
  reconciliation debt Story 4.3 already owns (the not-open/cancelled conflation, the
  double-counted-own-fill phantom trade) rather than a standalone fix.
