## Successes & Strengths

**The three-layer adversarial code review ran on all eight stories and produced a load-bearing find
in seven of them — the same 7-of-8-shaped result Epic 1 recorded, with no sign of diminishing
returns.** What it caught is qualitatively consistent: not "the code is wrong" but "the evidence that
the code is right does not exist."

- **2.1** — a lowercase bar type won the cross-strategy dedup and reached `load_ids` as an id IBKR
  cannot resolve; `live_market_data.py` names that outcome in its own comment as *"a silently dead
  subscription."* Plus six real behaviour holes in a model that had gone RED→GREEN in one pass.
- **2.3 — the epic's most serious defect, and it survived the story's own mutation testing.**
  `transition()`'s `SELECT … FOR UPDATE` took the row lock correctly and then discarded the locked
  row's values, because SQLAlchemy returned the identity-mapped instance and no `populate_existing`
  existed anywhere in `src/`. Reproduced twice against the live database: **two processes both
  reclaimed one session**, and a **`sealed` session moved back to `running`**. Neither the unit tier
  (repository mocked, no identity map) nor the shipped race test could reach it — the race test's
  loser uses a fresh `Session` whose identity map has never seen the row, the one arrangement in
  which the ORM *does* return fresh data.
- **2.4** — `check_redis_reachable` reported success for any endpoint that completed a TCP handshake
  without answering `+PONG`; the module docstring had argued that accepting-with-a-warning was the
  safer failure, and the premise was measured false. Separately: CI had **no redis service**, so the
  four integration tests proving the story's central guarantee always skipped.
- **2.5** — both escalated HIGHs were found independently by two layers, both in the reclaim design:
  the stop path had no ownership guard (a dispossessed incumbent would have transitioned the
  *successor's* row to `stopped`), and legitimate startup silence exceeded the 90-second staleness
  threshold, so a parallel `live start` could reclaim a healthy, still-starting session.
- **2.6** — **the regression the story exists for was still present.** `NautilusKernel._setup_loop`
  clobbers the signal disposition *inside* `_phase_node_build`, while the re-arm sat after the phase,
  so a Ctrl-C during the slowest stretch of startup was silently lost. And AC #9's bounded teardown
  was inert: measured `join_heartbeat` returning `False` in 0.00 s, then `dispose()` blocking
  **59.81 s** on the same wedged write.
- **2.7** — a `BaseException` from strategy code (`sys.exit()` in `on_bar`) escaped the guard's
  `except Exception` straight into the exact `os._exit(1)` the story exists to prevent. Found
  independently by two layers.
- **2.8** — three properties the ACs single out were provably unguarded *despite the story's own
  ten-mutation sweep*: setting `DEFAULT_HEARTBEAT_STALE_AFTER_SECONDS` to `9000.0` left all 2,335
  unit tests green; transposing closed/open trade counts passed all 67 tests; and `stale` — the
  health value AC #3 exists for — appeared **zero** times in the CLI and e2e test files.

**The practice escalated beyond what the Epic 1 retro asked for, twice, unprompted.** An *independent
refuter* layer was added at 2.2 (10 skeptics with repo access refuted 24 of 38 findings) and 2.4

- **2.2** settled five things the epic could not, including that `sa.Enum(SessionStatus)` persists the

## Challenges & Growth Areas

**A test that cannot fail is the defect class of this epic, and no single verification layer catches
it.** It appeared in every one of the eight stories. The important finding is not that it happened —
it is the measured ordering of what catches what:

| Layer | Catches | Structurally cannot catch |
|---|---|---|
| TDD Red-first | "the code does not do the thing" | a test whose assertion is satisfied by the fixture |
| Mutation of *predicted* guards | "this specific guard is inert" | any property the author did not predict was fragile |
| 3-layer adversarial review | "the test cannot fail"; "the AC is unguarded" | its own new tests |
| Mutation of the *review's* fixes | the reviewer's own vacuous tests | a path that has never executed |
| Live verification | "this whole path has never executed" | anything the procedure stops short of |

Story 2.6 states the problem plainly in its own task list — *"the single most-caught review finding
across Stories 2.1–2.5, in every one of them, is a test that cannot fail"* — mandated RED-first at
subtask granularity, and **shipped five vacuous tests anyway**. Story 2.8 ran ten mutations, killed
all ten, and still had three AC-named properties provably unguarded. The lesson is not "try harder";
it is that **mutation coverage must be selected from the AC list, not from the developer's model of
what is fragile**, and that each layer has to be run because the previous one is structurally blind
to its own output.

The variety is worth cataloguing, because the shapes recur:

- *Fixture data, not the guard.* 2.8's mutation #7 (drop list ordering) passed **vacuously** because
  the fixture's names — `newer-session` / `older-session` — happened to alphabetize the same as the
  intended order. Renaming to `zzz-` / `aaa-` made the two orderings disagree and the mutation died.
- *A substring against dense output.* 2.8 asserted `"3" in output` against output already full of
  digits from a UUID and an ISO timestamp. 2.2's migration guard asserted `"nullable=True" in text`,
  satisfied by nine unrelated occurrences.
- *A scan that scanned almost nothing.* 2.3's AR37 AST guard examined **4 of 192 files** and passed a
  planted probe, while its commit message claimed "no code path can write status any other way."
- *A double that cannot express the failure.* 2.5's controller fact needed a real `Trader` under
  `--forked`; 2.6's signal ownership needed a real `TradingNode`, because a `TestLiveNode` double
  constructs no kernel and therefore cannot clobber a handler.
- *A harness that lies.* 2.6's `join_heartbeat` bound test hand-built a coroutine that swallows
  `CancelledError` and installed no default executor — a shape production never produces. The test
  passed; the guard was unreachable.
- *A catch-all nothing reaches.* 2.8's new degraded-fallback branch was invisible because every flag
  set in the test hit a **named** branch.

**Stories claimed things about themselves that were not true, and the claims propagated.** 2.6's
completion notes said "all five Task 11 mutations" (four were run) and "every class under 100"
(`LiveSessionRunner` was 379). 2.7's `deferred-work.md` entry said a pin test existed — *"Pinned by a
test whose docstring says exactly this"* — and it did not; the Acceptance Auditor caught the false
claim and the test was written at review. 2.8 claimed a threshold pin it had not written. In each
case the claim was authored at drafting time as an *instruction* and read back at review time as a
*fact*. Epic 1's retro scoped this to sessions dying before commit; the real rule is broader:
**a claim of the form "pinned by a test" must cite the test's path and name, and any recorded claim
must be re-derived rather than trusted.**

**The 500 / 100 / 50 size caps broke comprehensively, and their interaction with the guard lists cost
real coverage.** Measured at `0602f1f`:

- 6 Epic 2 files over the 500-line cap: `live_session_runner.py` **734**, `live_strategy_guard.py`
  **635**, `session_service.py` **620**, `live_session_steady_state.py` **581**,
  `live_node_builder.py` **577**, `live.py` **538**. Four of them were **born over the cap.**
- 7 classes over 100: `LiveSessionRunner` **605** (6.0×), `StrategyGuard` **346**,
  `SessionSteadyState` **278**, `SessionStopSignals` **195**, `SqlSessionRecord` **155**,
  `SessionSpec` **135**, `StrategySpec` **130**.
- 15 functions over 50, topped by `build_trading_node_config` at **213** (4.3×).
- Repo-wide: **21 files over 500 and 195 functions over 50** already.
- **Nothing enforces any of it.** `pyproject.toml` selects `["E", "F", "I"]`; `line-length = 100` is
  the only size rule. No pre-commit check, no test.

The interaction is the part that actually hurt. Story 2.6's file-size split (`live.py` →
`live_start.py`) caused `live_start.py` to **silently escape two structural guards** — one of them

lists plus ~8 name lists govern the live path; a measurement today finds **7 `live_*` modules in
neither `NODE_FACING_MODULES` nor `EXEMPT_MODULES`**, and nothing asserts the union is complete, so
omission from both is silent. The guards' own comments record that they have already rotted. Cap
pressure forces splits; splits break hand-maintained lists; nothing notices.

**Every live procedure that could have found the order-path blockers was run on the epic's closing
day, in one session, after all eight stories were `done`.** The outcome was excellent — P8 passed all

**The deferred queue is growing faster than it drains, and seven threads have been deferred between

## Key Insights / Cross-Story Lessons

1. **Verification depth ratchets; each layer is structurally blind to its own output.** TDD cannot see
   a fixture-satisfied assertion. Mutation testing of predicted guards cannot see an unpredicted
   property. Adversarial review cannot see its own new tests — proven at 2.8, where 12 mutations
   against the review's own fixes found two survivors. And none of them can see a code path that has
   never executed, which is what live verification is for. **Run every layer; do not treat a lower
   one as evidence for a higher one.**
2. **"Market data arrives" is not evidence about orders; only an order reaching the broker is.**
   Recorded verbatim in `deferred-work.md` after two order-path defects sat in series for two epics,
   the first completely masking the second. The mechanism is instructive: the IB *data* client is
   built `venue=None` so Nautilus's default-client fallback adopted it, while the *exec* client is
   built `venue=IB_VENUE` so it never qualified. **Working market data actively concealed a dead
   execution path.**
3. **When a security or safety primitive is reused, assert what must SURVIVE, not only what must
   disappear.** `mask_account` is a whole-value masker: `mask_account("Error 321: account DU4076626
   is not managed")` returns `'***ged'`. The naive "the account id is absent" assertion stayed green
   against an implementation that destroyed the entire payload.
4. **An epic AC stated as a grep should be measured before the AC is accepted.** Two consecutive
   stories (2.2, 2.3) found the same epic-level gate literally unsatisfiable against the pre-existing
   codebase — `grep -rn "status = " src/` matches 20 lines that have nothing to do with sessions. The
   right response is 2.3's: change the instrument, preserve the property, and say so.
5. **A repo precedent can be exactly the wrong thing to copy.** The one existing DB enum
   (`ResolutionStatus`) dodges the `values_callable` footgun by making `name == value`, so copying it
   would have produced uppercase labels and silently-matching-nothing queries. And `create_type=False`
   copied from the same file is a *no-op* on `sa.Enum` while being load-bearing on
   `postgresql.ENUM` in a migration.
6. **Naming a recurring failure mode inside the story does not prevent it.** Stories 2.1, 2.4 and 2.6
   each quoted the Epic 1 retro's documentation-overstatement finding in their own text, warned the
   dev agent about it explicitly — and then committed it, and review caught it, in all three. A
   warning is documentation; only an executable check is a gate.
7. **A pre-agreed file-split line, chosen before knowing where the review will land, is optimistic.**
   Story 2.6 pre-agreed a split that was "not the phase sequence and not the `finally`" — which is
   exactly where every one of the review's fixes had to go. Budget for two splits, or accept the
   overage explicitly.
8. **Return code, not log assertions, is the only reliable proof on an `os._exit` path.** It discards
   buffered stdout (measured: 0 bytes), skips `atexit`, every `finally`, and the async Rust log
   flush; the explanatory ERROR line survived only 4 of 20 runs.
9. **A structural guard's *scope* matters as much as its assertion, and must be measured.** "How many
   files does this scan actually examine?" is a question with a number as its answer. 2.3's answer
   was 4 of 192. Every AST guard in the live path now carries a non-vacuity assertion against a
   planted probe — and 2.6 adds the refinement: the probe must be one the story controls, never a
   real defect the next story is going to delete, or the guard and its non-vacuity proof die
   together.

## Epic 3 Preview & Dependencies

Epic 3 ("Live Order Execution & Trade Capture", FR23–FR31) is fully defined in `epics.md` with 7
stories, all `backlog`. Its standalone deliverable is the phase's first complete round trip: entry
submitted → filled → position opened → exit filled → trade persisted with real fills and real
commission.

**Direct dependencies on Epic 2 work, and their state:**

- **`trader_id` (Story 2.4 / AR10)** — done and live-verified. Story 3.2 AC #2 requires client order
  IDs from Nautilus's deterministic generator "operating under the session-stable `trader_id` from
  Story 2.4." This is `epics.md`'s stated *one hard cross-epic ordering constraint*, and it is met.
- **Redis per-session namespace (2.4)** — done; `use_instance_id=False` proven end to end against a
  real node, and pinned by a permanent inverted test.
- **The migration (2.2)** — done. `trades.session_id`, nullable `trades.backtest_run_id` and the
  CHECK constraint were shipped specifically for E3/E5 and are unconsumed until Story 3.6.
- **State machine (2.3, AR37)** — done. Nothing in Epic 3 may set `status` directly; the AST guard
  now scans all of `src/` with a two-file allowlist.
- **Runner + ordered startup (2.5, AR39)** — done. Story 3.2's permission suppression sits in the
  `trading` phase; Story 3.4's AR25 cache load must occupy the `reconcile` slot the runner reserved.
- **Strategy failure guard (2.7)** — done, and **under-documented in `epics.md`**: 2.7's AC #1 states
  the guard covers `handle_bar` today and that **`handle_event` is the Epic 3 path**, covered by the
  same guard. Every order, fill and rejection event Epic 3 handles passes through Epic 2's wrapper.
  `deferred-work.md` records why it is already there so Epic 3 does not "tidy" it away as premature.
- **`status` / `list` (2.8)** — done. Story 3.7 AC #3 (repeated rejections visible from `status`)
  and 2.8's `closed_trade_count` both wait on Epic 3 rows; the count has only ever returned 0.
- **The pinned flatten test (2.6 AC #2)** — Story 3.1 must delete **both**
  `sma_crossover.on_stop()`'s `close_all_positions()` call and the Story 2.6 test that asserts it
  still flattens. That test's docstring says so.

**Gaps Epic 3 inherits, ranked by risk to its deliverable:**

1. **The submit path is proven to submission and never to a fill.** Both order-path defects are fixed
   and `ExecClient-INTERACTIVE_BROKERS: Submit MarketOrder(SELL 22 NVDA.NASDAQ …)` appeared live — a
   line that had never appeared in any transcript. But no `OrderFilled`, no `PositionOpened`, no
   commission value has ever been observed. **Epic 3 begins with zero live evidence that the second
   half of a round trip works.** Story 3.2 owns the verification.
2. **Story 3.1's premise has never been observed.** Because no session ever traded, the
   `on_stop()` flatten that 3.1 removes has never been exercised against a session-owned position.
   The warnings P6, P7 and P8 all carry about it are untested assumptions. Story 3.1's before/after
   backtest comparison will be the only evidence path that exists for the edit.
3. **A subscription-killing IB error class with nothing retrying it — now three instances** (10182

## Significant Discoveries

No Epic 3 **scope** rewrite is required — its ACs describe the right work. Three findings are
concrete enough to flag prominently rather than let surface mid-implementation.

> **1. Two defects sat in series on the order path for two epics, each completely masking the next,
> and nothing in the automated suite noticed either.** `InteractiveBrokersExecClientConfig` was built
> with no `routing=`, so it served only the `INTERACTIVE_BROKERS` venue while every instrument this
> codebase trades carries the exchange as its venue — `ExecEngine` refused every order with *"no
> execution client configured for NASDAQ."* Fixing that immediately revealed the second: the exec
> client's `instrument_provider` was never loaded, and the adapter dereferences
> `instrument_provider.find(...).is_inverse` with **no `None` check**
> (`adapters/interactive_brokers/execution.py:525`), so the first order ever to reach the client died
> as an `AttributeError` **inside the adapter's own `submit_order`** — where the strategy sees no
> rejection and no `OrderDenied`. The order simply stops.
>
> Both are fixed (`90337eb`) with regression tests that drive Nautilus's real `TradingNodeBuilder`,
> including an anti-tautology twin that counts **zero** under the stock `RoutingConfig`. **This is
> not an Epic 2 failure** — no Epic 1 or Epic 2 acceptance criterion asserts that an order reaches
> the broker. What was happening is that Story 2.5 starts *real* strategies, so `sma_crossover` was
> **attempting** orders as a side effect of a feature that never claimed them, and the attempts
> failed silently. **Story 3.2 inherits both as landed groundwork and owns their live verification.**

> **2. A competing IBKR login silently kills a running session's market data, and nothing in the
> session says so.** On 2026-08-28 four consecutive sessions received zero bars because IB answered
> every subscription with code 162, *"Trading TWS session is connected from a different IP address."*
> Ruled out by experiment: stale client id (reproduced on id 17) and contract-specificity
> (reproduced on MSFT and NVDA). Cause confirmed by the operator — an IBKR mobile-app sign-in
> mid-session. IBKR permits one active session per account, so the login evicted the Gateway's
> market-data entitlement **while leaving its API socket up**: the session connected, passed both
> gate layers, logged `Subscribed … bars`, and kept heartbeating while receiving nothing.
>
> **Operational rule for every live procedure from here on: do not use the IBKR mobile app or client
> portal while a session is running.** The three transcript codes to grep for are **162**, **10182**
> and **366**.

> **3. Epic 2 amended eight of its own acceptance criteria, and `epics.md` records none of them.**
> Every amendment lives in a story file: 2.2's repository *name* deviation (knowingly unmet on the
> letter, met on the substance); 2.3's grep-to-AST instrument change and its added concurrent-reclaim
> AC #6; 2.6's knowingly-unmet AC #2 clause plus three added ACs; 2.7's re-reading of AC #1 and AC #2
> plus six added ACs and a **second migration** that falsified the "single migration" framing; 2.8's
> upheld `--json` contract and accepted exit-4-on-DB-failure. **If Epic 3's stories are drafted from
> `epics.md` alone, they will inherit wording Epic 2 already proved wrong** — including the "phase's
> single migration" budget argument that has been used to defer the fencing column three times.
