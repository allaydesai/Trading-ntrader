## Successes & Strengths

**The technical throughline held.** 4.1's foundational technique — classify a broker read from
the adapter's own request future rather than trusting its ambiguous return value (F1–F3: `None`
means timeout, disconnect, *or* zero positions, indistinguishably) — was reused conceptually by
every later broker-read in the epic. 4.2's "refuse, don't correct" ruling (D-D) became the
template every later story followed: disclose every alternative, PO picks one, document the
reasoning in the story file rather than in review comments.

**Real defects were found by building the feature, not by looking for them.** 4.4's momentum SMA
bug (above). 4.2's Task 1 pre-build measurement found something *worse* than drafted: a shrunk
re-entry on a pre-4.5 namespace doesn't just fail reconciliation, it **Rust-panics the whole
process** — uncatchable in Python, before any of our code runs. 4.5 then closed it (D-A + D-D) as
the single most severe finding traced across the whole epic.

**Governance infrastructure landed as Epic 3 retro pre-work paid for itself immediately.** D2
(Postgres CI), D3 (`exit_outcome` markers) and D4 (the AST size-cap guard) were operationalized
into a dedicated pre-work spec (`epic4-prework-spec.md`) *before* any Epic 4 story started, and
all three were then exercised constantly — budget splits, baseline entries with disclosed
reasons, marker-based exit-code classification. This is the strongest evidence in the project's
history that a retro action item lands when it's turned into pre-work rather than left as prose
to remember later.

**The PO's fallback-condition ruling became a real, generalized process improvement mid-epic.**
Story 4.5's D-F drafted a fallback rule ("if the cache can't hold the watermark reliably, bring it
back to the PO"). Task 1.4 measured that condition literally true; the dev built the alternative
anyway without reporting back. Review caught it. The PO's ruling — accept the build, but instruct
that a literally-met fallback condition always comes back for a ruling, never gets judged
unilaterally — was immediately generalized and is now a standing project rule
(`feedback_literal_fallback_conditions` in project memory). This retrospective itself exercised
that same rule on P19a's discrepancy (see Decisions Ruled, below).

**Mutation sweeps stayed honest.** 4.6's M4 (a mutation counting closed positions) survived and
was accepted as a documented equivalent mutant rather than papered over with an artificial test —
rigor applied to knowing when *not* to chase a number, not just to hitting one.

## Challenges & Growth Areas

**Financial-safety HIGH findings kept surfacing at review, not at draft, in three separate
stories.** 4.6's account-normalization mismatch (`TWS_ACCOUNT` compared raw instead of
`.strip().upper()`'d, so any lowercase or padded account value exited 5 on *every* run). 4.5's
strategy-refusal path silently renumbering every later strategy's `order_id_tag`, orphaning
restored positions. 4.7's own safety-doc claim about corporate-action absorption, provably false
for the bundled `sma_crossover` strategy once a synthetic triple formed. Same shape three times:
implementation consistently missed a cross-cutting interaction that a second adversarial pass
caught. Worth naming as a pattern, not three unrelated near-misses — a review checklist item
("does this interact with account normalization / order numbering / the bundled strategies'
actual behavior, not just the story's own happy path?") might catch this earlier next time.

**No story ever completed its own live IBKR run within its own dev-story session — by design, but
the story-level evidence trail looked incomplete as a result**, and the trail stayed incomplete
until this retrospective. Every P14–P20 procedure sat at "defined, not run" in the committed QA
doc even after a live E2E pass had actually closed most of them on 2026-09-28. That pass's results
were never written back into `docs/qa/phase3-live-verification.md` — this retrospective did that
write-back (see Decisions Ruled). Worth a standing habit: a live E2E pass should update the QA doc
in the same session it runs, not leave that for a later retrospective to notice and reconcile.

**The runner file's size cap was a slow-burn, epic-long pressure, not a one-off.** 4.1 closed
499/500. 4.4 closed 499/500 *again*, with an explicit flag that it left no headroom for the two
parallel stories (4.2, 4.3) still landing. Both of those needed their own pre-planned budget
splits before any feature code. Nobody blew the cap, but the whole epic lived right against it —
worth a proactive split at the start of Epic 5 rather than waiting for the next story to hit the
wall.

**A recurring, moderately expensive test-flake category kept showing up and was never
structurally fixed.** Component-tier CPU-starvation flakiness surfaced in 4.1 (parallel unit +
component run caused 12 spurious failures, fixed by running sequentially), 4.2 (an intermittent
`NoStrategyStartedError`, root-caused and fixed with a new test seam), 4.6 (a transient flake
matching the known pattern), and 4.7 (a genuine cross-file `asyncio.set_event_loop(None)`
isolation leak from 4.2/4.3's real-engine harnesses, found and locally fixed). 4.7's own review
explicitly deferred a structural fix at the conftest/fixture level as "the owner's call" — it
still has no owner. This retrospective independently found and fixed a related but distinct
isolation bug during the `trade_size` default fix (below) — the same *class* of problem
(environment/fixture state bleeding across tests under parallel execution) keeps recurring across
the whole project, not just this epic.

## Key Insights / Cross-Story Lessons

- **A deliberate trade-off, once made, needs its consequence tracked as a first-class item, not
  just accepted and forgotten.** PO ruling 1A (Story 4.3) kept Nautilus's native open-order
  consistency check off because turning it on breaks Story 3.7's refusal-streak invariant worse
  than the problem it would fix. That's the right call — but its cost (a stranded `ACCEPTED` order
  is never cleared) sat as "carried forward, still conditional" for two full stories (4.3, 4.5)
  without anyone actually designing a fix, because nothing forced the question until a
  retrospective did. See Decisions Ruled, Story 4.8.
- **"Owner: Epic 4 retrospective," used as a disposition by name across five stories (4.1, 4.3
  ×2, 4.5 ×2), is a real mechanism, not a placeholder — this retrospective's actual job was
  closing those named items, not just discussing the epic.** That framing (borrowed from the
  story-synthesis agent's own observation) turned out to be exactly right and shaped this retro's
  agenda more than a conventional "what went well" discussion would have.
- **Evidence-first policy changes keep paying off.** 4.7 proved its corporate-action coverage-rule
  relaxation was a strict superset of the old refusal rule via a 63-row truth table *before*
  shipping it — the same discipline as 4.1's "measure before believing the framework" habit that
  opened the epic.

Epic 5 ("Seal a Session & Compare It Against Its Backtest") covers FR40–FR47: an explicit seal
turns a stopped session into an ordinary run record through the same `ResultsExtractor` a backtest
uses, appearing beside its backtest in the existing comparison view with **zero UI changes** — a
stated success criterion, not an omission. 6 stories planned (5.1–5.6), all still `backlog`.

**Direct dependencies on Epic 4 deliverables:**
- **Story 5.1** (compute metrics for a live host) inherits a hard, already-identified constraint
  from Story 4.1: the live-host extractor must never read IB `AccountState.total`/`NetLiquidation`
  as cash or equity — the adapter can invent a value (the known `400000` bug) under margin stress.
  This should be an explicit acceptance criterion in 5.1's draft, not inherited tribal knowledge.
- **Story 5.4** (record the conditions the session actually ran under, incl. `price_basis`) may be
  under-scoped against what 4.7 found: a corporate-action-affected lot's P&L reads at unadjusted
  prices (a 2:1 split reads as ~50% loss), and the split's extra shares sit in a synthetic
  `EXTERNAL`/`INTERNAL-DIFF` position that is **never recorded as a trade at all**. As currently
  described, 5.4 is one metadata label — it is not yet clear a label alone is enough for 5.2's
  equity-curve reconstruction (built purely from the trades table) to be correct for a session that
  absorbed a corporate action. **Flagged for explicit review when 5.2/5.4 are drafted, not a
  re-plan.**
- **Moderate-confidence, unconfirmed risk:** Epic 4's synthetic-position architecture
  (reconciliation-owned `EXTERNAL`/`INTERNAL-DIFF` positions, deliberately excluded from trade
  persistence since Story 3.6 D-D) means a sealed session that underwent any reconciliation
  correction during its life may have economic activity that never appears in the trades table
  Story 5.2 reconstructs from. Worth a question at Epic 5 planning, not a settled finding.
- **No epic-blocking discovery.** Nothing found during Epic 4 requires Epic 5's plan to change
  before drafting starts; the items above are checks to run during 5.1/5.2/5.4 drafting, not
  reasons to re-plan the epic.

## Story 4.8

Commissioned at this retrospective to close the stranded-`ACCEPTED`-order item rather than
re-route it a third time. File:
`_bmad-output/implementation-artifacts/4-8-clear-a-stranded-order-after-a-broker-confirmed-fill-or-cancel.md`
(status `ready-for-dev`), added to `epics.md`'s Epic 4 section as a post-retro addition, and
`sprint-status.yaml` updated (`epic-4` reopened to `in-progress` — an epic is only `done` when
every story is, and 4.8 is now one of its stories; the retrospective itself stays `done`
regardless).

**Design, in short.** Nothing today ever resolves a stranded `ACCEPTED` order — verified, not
assumed, across three independent code paths (startup reconciliation only corrects positions;
Nautilus's own startup/consistency passes only reconcile broker reports that exist, never noticing
one that's *missing*; the runtime reconciler deliberately defers only in-flight orders). The fix:
a new module (`src/core/live_stranded_orders.py`) composed into the existing `RuntimeReconciler`
(Story 4.3), running once per runtime cycle — never on reconnect cycles, never at startup. It
makes a defensive, wrapped call to the broker's open-orders list (any failure is "inconclusive,"
never propagated — the same empty-`orderRef` landmine Story 4.3 already found), debounces a
confirmed-absent order across two cycles ≥60s apart, then resolves it through
`reconcile_execution_report` — the same framework-native path positions already use, not a
forbidden order method and not a broker call. The native open-order consistency check (PO ruling
1A) is explicitly untouched.

**Honest limitation, disclosed rather than glossed over:** this fix runs strictly after
`node:connect` completes. It cannot prevent or explain a hang *inside* Nautilus's own startup
sequence — which is what the historical `p7-position-test` stall actually was, and which Story
4.3's own Task 1.5 already tried and failed to reproduce even with a real engine+cache+portfolio
harness. The story is explicit that it closes the "order stays `ACCEPTED` forever" half
concretely, and that the stall's true root cause remains unconfirmed — routed to a new,
operator-only live Procedure P21.

**Two decisions were flagged ⚖️ for Allay's ruling before Task 3 (implementation) could start,
rather than decided by the drafting agent — both ruled the same day, as recommended:**

- **D-C — RULED (A): a stranded order always resolves to `CANCELED`**, with a record disclosing
  the true outcome (fill vs. cancel) couldn't be determined here — the existing position-level
  correction (`INTERNAL-DIFF`) already carries the real economic effect if it was actually a fill.
  Rejected: inferring `FILLED` from position evidence (the same kind of cache-surgery
  reattribution Story 4.2's PO already refused once), and log-only (leaves the original problem
  unsolved).
- **D-G — RULED (A): Task 1 re-confirms Story 4.3's existing (negative) stall-reproduction
  finding once more and stops there** — building a full `NautilusKernel`/`TradingNode`
  integration-tier harness specifically to hunt for the `node:connect` hang is real, separate
  scope this project's own component-tier discipline already forbids attempting casually, and
  Story 4.3 already tried the next-best thing and found nothing.

No open rulings remain in Story 4.8 — it is genuinely `ready-for-dev`.
