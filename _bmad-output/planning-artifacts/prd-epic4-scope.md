## Scope Boundary

This run delivers **Epic 4: Stop, Restart & Resume Mid-Position** only. Epics 1–3 are
`done` on `015-paper-trading` (Epic 3 closed 2026-09-22 with live Procedure P13): the
system connects to IBKR paper behind the two-factor real-money gate, owns durable
sessions that outlive process runs, and submits, tracks, aggregates and persists real
orders and trades. Epic 5 (seal + compare) is **out of scope** and must not be started.

**Standalone deliverable:** a session survives a full process stop/restart **while holding
an open position** and resumes mid-position with warm indicators and broker-confirmed
state, with no artificial exit generated by the stop. Plus `ntrader live reconcile`
reporting any discrepancy explicitly.

**The phase's truth-test:** this is the external-authority check that Phase 1 got from
row-count parity and Phase 2 from FMP price validation. Without it, every downstream
metric rests on self-report.

**What already exists that Epic 4 fills in (do not reinvent):**
- `PHASE_SEQUENCE` in `src/core/live_session_phases.py` already contains `reconcile` and
  `warmup`; both are declared **no-op placeholders** in `src/core/live_session_runner.py`
  (`_phase_reconcile`, `_phase_warmup`). Stories 4.2 and 4.4 give them bodies.
- Nautilus execution reconciliation is already switched on in `src/core/live_node_builder.py`
  (`EXEC_ENGINE_RECONCILIATION = True`, `NODE_TIMEOUT_RECONCILIATION = 30.0`). Story 4.2
  proves and enforces it rather than re-enabling it.
- `ConnectionMonitor.confirm_state_reestablished()` (`src/core/live_connection_monitor.py`)

- `sma_momentum.on_start()` already calls `request_bars` then `subscribe_bars`;

- There is **no** `live reconcile` CLI command yet (Story 4.6).

## Governing Journeys (from `prd.md`)

### Journey 2: Stop, Restart, Resume — the Signature Journey

Allay stops the process. **Positions stay open at IBKR** — untouched, exactly as a swing
strategy requires. Overnight the gateway restarts; nothing is running, nothing to break.
Next morning Allay starts the process again. Before any strategy runs, startup
reconciliation asks IBKR what's actually there: two open positions, at these prices, this
size. That answer — **not local state** — hydrates the cache. Indicators re-warm from
historical bars. Only then do strategies start. The strategy resumes *mid-position*: it
knows it's long, so it's looking for an exit and its stop level — not a fresh entry.
**Nothing about the interruption is visible in the trade record.** Trade eleven lands in
the same record as trade one.

### Journey 3: Reconciliation & Trust

Allay runs the reconciliation check. The system asks IBKR for positions and cash on the
account and compares against its own view, line by line. They match — or a discrepancy is
named explicitly: *this instrument, this quantity, this much cash.* No silent averaging, no
"close enough." The metrics rest on state that the broker itself confirms.

### Broker-Authoritative State & Corporate Actions

- **IBKR's account view is truth for positions and cash.** Local state is a cache that
  defers to it on any conflict — never the reverse. Startup reconciliation establishes it;
  continuous reconciliation maintains it.
- **Corporate actions land live and unadjusted.** Over a multi-week swing session, a split
  or dividend will eventually change position size or cash. Broker-authoritative state
  absorbs them automatically; reconciliation makes them visible rather than silent.
- **A reconciliation discrepancy is reported, never auto-resolved by trusting local state.**

## Functional Requirements — State Reconciliation & Resume (E4)

- **FR32:** System can retrieve the broker's authoritative view of positions and cash for the
  configured account.
- **FR33:** System can reconcile internal order and position state against the broker's state at
  session start, before any strategy begins trading.
- **FR34:** System can maintain alignment between internal state and broker state throughout a
  running session.
- **FR35:** System can resolve any conflict between internal state and broker state in favor of
  the broker.
- **FR36:** Operator can request an on-demand reconciliation check and receive an explicit report
  of any discrepancy found.
- **FR37:** System can restore strategy indicator state from historical data before that strategy
  begins processing live data.
- **FR38:** System can resume a strategy mid-position, such that it continues seeking exits and
  stop levels for positions opened during a prior process run.
- **FR39:** System can absorb position and cash changes arising from corporate actions via
  broker-authoritative state.

Cross-cutting requirements the stories also cite: **FR5** (reserved client IDs — the
reconcile command uses `ibkr_live_client_id + 1`), **FR19** (trades before and after a
restart belong to the same `session_id`).

## Non-Functional Requirements Governing Epic 4

Selected from the full NFR set as the ones Epic 4 is accountable for.

- **NFR3:** A session started 5 minutes before the market open is trading at the open
  (connect → reconcile → warm indicators → subscribe all complete within that window).
- **NFR5:** A reconciliation check completes in < 30 seconds.
- **NFR9:** Resume correctness — after any restart, internal position state matches the
  broker's exactly (**0 discrepancy**) before any strategy is permitted to trade.
- **NFR10:** No blind trading — zero orders submitted while the execution client is
  disconnected or while reconciliation is incomplete.
- **NFR14:** No artificial trades — no stop, restart, disconnect, or reconnect generates an
  entry or exit the strategy did not request.
- **NFR15:** Rate-limit compliance — the existing 45 req/s discipline governs live requests;
  historical warm-up requests respect IBKR pacing rules.
- **NFR18:** Reconciliation is mandatory, not optional — every session start reconciles
  against the broker; no path starts trading on unverified state.
- **NFR20:** Safe degradation — when IBKR is unreachable the session halts trading safely and
  reports it; it never estimates, assumes, or proceeds on stale state.
- **NFR32:** Automated tests never touch a real broker — reconciliation logic is tested
  against broker doubles across the existing unit / component / integration (`--forked`)
  tiers.
- **NFR33:** Broker-dependent behavior is verified by operator-run procedures against the
  real paper account (restart resume, reconciliation) — the phase-gate evidence, which
  cannot live in CI. **For the traceability gate:** an acceptance criterion whose only
  possible proof is a live broker (a real stop/restart across an open position, a real
  corporate action, wall-clock timing against IBKR) is satisfied by (a) a broker-double test
  of the same logic **and** (b) a documented operator procedure in
  `docs/qa/phase3-live-verification.md`. It is not "unmet" because CI cannot run it.

## Architecture Requirements Governing Epic 4

- **AR22:** No CI/CD changes; no deployment artifacts. Operator-run verification procedures
  against the paper account are documented in `docs/qa/phase3-live-verification.md`.
- **AR25:** Startup reconciliation loads working orders into the cache before strategies
  start, so a resumed strategy sees its own open orders.
- **AR34:** The `reconcile` command connects read-only with `ibkr_live_client_id + 1`.
  Documented client-ID reservation: historical = `IBKR_CLIENT_ID`, session =
  `ibkr_live_client_id`, reconcile = `+1`.
- **AR38:** The runner owns the node; the service owns the record. `LiveSessionRunner` never
  imports SQLAlchemy; `SessionService`/repositories never import Nautilus.
  `live_trade_recorder` is the single sanctioned bridge where Nautilus objects meet the DB.
  Broker state retrieved for Epic 4 is converted to domain types at the boundary.
- **AR39:** Startup sequence is explicit, ordered, and logged as phases:
  `gate:static → node:build → node:connect → gate:account → reconcile → warmup → subscribe → trading`.
  Each phase logs `phase=<name> status=started|ok|failed`. Agents must not reorder, merge,
  or skip phases; a failure in any phase stops the sequence.
- **AR40:** Mode-agnostic strategies. Indicator warm-up in `on_start()` uses only
  mode-agnostic Nautilus APIs (`register_indicator_for_bars`, `request_bars`,
  `subscribe_bars`). Grep-enforceable: `is_live` count = 0 in `src/core/strategies/`.
- **AR41:** Log event naming — dotted lowercase past-tense in a sanctioned namespace
  (`reconcile.*`, `warmup.*`, `connection.*`, …). Normative milestones this epic owns:
  `reconcile.ok`, `reconcile.discrepancy`, `warmup.completed`, `connection.restored`.
- **AR43:** Anti-patterns to reject in review: `close_all_positions()` in any lifecycle hook;
  retry-on-timeout around order submission; reading `ibkr_read_only` as the safety control.

## Epic 4: Stop, Restart & Resume Mid-Position

Swing strategies become viable. The operator stops overnight with positions open, restarts in the
morning, and — before any strategy trades — the system hydrates from IBKR's authoritative view,
re-warms indicators from history, and only then subscribes to the live stream.

**Covers:** FR32–FR39 · NFR3, NFR5, NFR9, NFR10, NFR14, NFR18 · AR25, AR34, AR39

### Story 4.1: Read the Broker's Authoritative View of Positions and Cash

As the operator,
I want the system to be able to ask IBKR what it actually holds,
So that every downstream check has an external authority to compare against rather than trusting
itself.

**Acceptance Criteria:**

**Given** a connected session
**When** broker state is requested
**Then** positions (instrument, quantity, average price) and cash balances are retrieved for the
configured account (FR32).

**Given** the retrieved state
**When** it is represented internally
**Then** it is converted to domain types at the boundary, so nothing downstream depends on Nautilus
or IBKR types (AR38).

**Given** an account with no positions
**When** state is retrieved
**Then** an empty result is returned successfully and is distinguishable from a failed retrieval.

**Given** retrieval fails or times out
**When** the error surfaces
**Then** it is reported explicitly and never silently treated as "flat" (NFR20).

**Given** the retrieval
**When** it is timed
**Then** it completes within 30 seconds (NFR5).

### Story 4.2: Reconcile Against the Broker Before Any Strategy Trades

As the operator,
I want startup to hydrate from IBKR's answer rather than from local state,
So that a resumed session begins from what is actually true at the broker.

**Acceptance Criteria:**

**Given** the startup sequence
**When** the `reconcile` phase runs
**Then** it executes after `gate:account` and strictly before `warmup`, `subscribe`, and `trading` —
no strategy is started until reconciliation has completed (FR33, NFR18, AR39).

**Given** Nautilus's native reconciliation
**When** the node is configured
**Then** startup reconciliation is enabled through framework configuration rather than reimplemented,
and working orders and open positions are loaded into the cache (FR33, AR25).

**Given** a disagreement between cached state and broker state
**When** reconciliation resolves it
**Then** the broker's view wins and the cache is overwritten — never the reverse (FR35).

**Given** reconciliation has not completed
**When** a signal would fire
**Then** no order is submitted (NFR10).

**Given** reconciliation completes
**When** state is compared
**Then** internal position state matches the broker exactly — **0 discrepancy** — before trading is
permitted (NFR9).

**Given** reconciliation fails
**When** the phase reports
**Then** it logs `phase=reconcile status=failed`, the startup sequence stops, and the session does
not trade (AR39).

### Story 4.3: Keep Runtime State Aligned with the Broker

As the operator,
I want alignment maintained while the session runs, not just at startup,
So that a multi-week session does not drift away from reality between restarts.

**Acceptance Criteria:**

**Given** a running session
**When** continuous reconciliation is configured
**Then** it runs throughout the session using Nautilus's native machinery (FR34).

**Given** a discrepancy detected at runtime
**When** it is resolved
**Then** it resolves broker-ward and is logged as `reconcile.discrepancy` with the specific
instrument and quantities (FR35, AR41).

**Given** no discrepancy
**When** a reconciliation cycle completes
**Then** `reconcile.ok` is logged at a volume that does not drown the trading log.

**Given** a reconnection after a disconnect
**When** the connection is restored
**Then** state is re-established before trading permission returns (NFR10).

### Story 4.4: Warm Indicators from History Before the Live Stream Starts

As the operator,
I want every strategy's indicators primed with historical bars before the first live bar arrives,
So that a restarted session does not trade on cold indicators or sit silent for a week waiting for
them to fill.

**Acceptance Criteria:**

**Given** `sma_crossover.py` and `sma_momentum.py` — which today only call `subscribe_bars`
**When** `on_start()` is rewritten
**Then** each registers its indicators via `register_indicator_for_bars()` and requests history via
`request_bars(...)`, with `subscribe_bars` invoked from the history callback so the live stream
starts only after history has loaded (FR37, AR40).

**Given** the rewritten `on_start()`
**When** it is inspected
**Then** it uses only mode-agnostic Nautilus APIs and contains no branch on execution mode — `is_live`
count remains 0 (AR40, AR43).

**Given** the same strategy in a **backtest**
**When** it runs before and after this change
**Then** it behaves identically in both engines, with any difference explained solely by indicators
being warm at the first traded bar (AR40).

**Given** a started session
**When** the first live bar arrives
**Then** every registered indicator already reports initialised, and `warmup.completed` was logged
before the first bar was processed (FR37, AR41).

**Given** the warm-up requests
**When** they are issued
**Then** they respect IBKR historical pacing rules (NFR15).

**Given** a session started 5 minutes before the market open
**When** the full sequence runs
**Then** it is subscribed and trading by the open (NFR3).

### Story 4.5: Resume a Strategy Mid-Position

As the operator,
I want a restarted strategy to know it is already long and to keep hunting the same exit,
So that a multi-day swing trade survives my daily restarts without leaving a trace in the trade
record.

**Acceptance Criteria:**

**Given** a session stopped while holding an open position
**When** the process is restarted
**Then** the strategy resumes aware of that position and seeks exits and stop levels for it, rather
than treating the instrument as flat and opening a fresh entry (FR38).

**Given** the resumed position
**When** its identity is checked
**Then** it is the same position the broker reports — hydrated from reconciliation, not reconstructed
from local state (FR35).

**Given** a full stop/restart cycle across an open position
**When** the trade record is examined afterwards
**Then** it contains no entry or exit generated by the interruption — the eventual round trip reads
as one trade (NFR14).

**Given** the restart
**When** the strategy's first live decision is made
**Then** it happens only after reconciliation and warm-up have both completed (NFR9, NFR10).

**Given** the resumed session
**When** its identity is checked
**Then** the trade closed after the restart belongs to the same `session_id` as trades from before it
(FR19).

### Story 4.6: Check Positions and Cash Against IBKR on Demand

As the operator,
I want to run a reconciliation check whenever I want reassurance,
So that I can confirm the system's picture of reality matches what TWS shows me.

**Acceptance Criteria:**

**Given** `ntrader live reconcile <session>`
**When** it is run
**Then** it connects read-only, retrieves broker positions and cash, compares them against the
session's local view, prints an explicit result, and disconnects (FR36).

**Given** the command runs while a session process holds `ibkr_live_client_id`
**When** it connects
**Then** it uses `ibkr_live_client_id + 1`, so it never evicts the running session (FR5, AR34).

**Given** a discrepancy
**When** it is reported
**Then** the report names the specific instrument, the expected and actual quantities, and the cash
difference — no averaging, no "close enough" (FR36).

**Given** any discrepancy
**When** the command completes
**Then** it reports and exits — it never auto-resolves by trusting local state (FR35).

**Given** matching state
**When** the command completes
**Then** it reports a clean result explicitly and exits `0`.

**Given** the check
**When** it is timed
**Then** it completes within 30 seconds (NFR5).

### Story 4.7: Absorb Corporate Actions Through Broker-Authoritative State

As the operator,
I want a split or dividend during a multi-week session to be picked up and made visible,
So that a position size changing underneath me is an observation rather than a silent corruption.

**Acceptance Criteria:**

**Given** a corporate action changes a position's size or the account's cash at the broker
**When** reconciliation next runs
**Then** the change is absorbed from the broker's view without manual intervention (FR39).

**Given** such a change is absorbed
**When** it is logged
**Then** it appears as an explicit reconciliation event naming the instrument and the before/after
quantities — visible rather than silent (FR36).

**Given** the divergence between adjusted backtest prices and unadjusted live prices
**When** the phase's documentation is written
**Then** it is recorded as an expected structural property of the comparison, not a defect to chase
(carried into `session_conditions` in Epic 5).

**Given** the operator verification procedures
**When** `docs/qa/phase3-live-verification.md` is written
**Then** it documents the manual procedures for connectivity, gate refusal, a complete round trip,
restart resume, and reconciliation — the phase-gate evidence that cannot live in CI (NFR33, AR22).
