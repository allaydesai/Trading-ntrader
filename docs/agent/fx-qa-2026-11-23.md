# FX backtesting: end-to-end QA (2026-11-23)

QA of the unmerged FX stack (#63 M4 -> #64 M5 -> #65 M6 pin, strategies#4) on real
`firstrate-fx` data, through the CLI, the research MCP server (stdio) and the dashboard. Code
under test: `feat/fx-m6-pin` `fc6bf08`, strategies `7cba5af`. Fixes are on `feat/fx-qa-fixes`
(this branch) and strategies `feat/fx-qa-fixes` (PR #5).

**Verdict:** FX results are correct. For every QA run the sum of the trade rows' USD P&L
equals the account's balance change, and an independent hand check reproduces every
trade's USD P&L, commission and spread. Exceptions: the documented rounding (+-0.02), and
one Riptide trade hit by a stop bug, now fixed. CLI, MCP and dashboard show the same numbers.
Two bugs fixed (one in the strategies repo), the rest listed below.

## How it was checked

- **Hand check** (scratch script, independent of the app's FX code): for each trade it reads
  the stored average prices, quantity and timestamps, plus the catalog's `MID` bar closes.
  From those it recomputes pips, quote-currency P&L, the USD conversion, commission
  `max(0.20 bp x USD value, USD 2.00)` per order, the half-spread
  `units x spread_pips x pip / 2` per side, USD notional and 3% margin, and compares them with
  `trades.profit_loss`. Conversion rates, as found:
  - USD quote (EURUSD, GBPUSD): 1.
  - USDJPY P&L: `1 / close` of the fill bar for `on_bar` market orders; of the **previous**
    bar for resting stops and limits and for gap-aware fills (the documented lag, pinned in M3).
  - USDJPY **spread**: `1 / fill price` (closed form in `usd_per_quote`), not the cache rate.
    That is by design, but a hand check that converts it at the bar close is off by up to
    USD 0.33 a trade.
  - EURGBP: the GBPUSD close of the fill bar.
- **Sum check**: `sum(trades.profit_loss)` vs `final_balance - initial_capital`, all runs.
- **Cross-surface**: the same run read through `backtest show`, MCP `get_run`/`compare_runs`/
  `export_results`, the dashboard run page (FX panel), the trades-table fragment, the CSV/JSON
  exports and the chart/statistics APIs.
- **EURGBP**: there is no cross data on the VPS. A **synthetic** EURGBP 1-hour series
  (`EURUSD / GBPUSD` per bar, 2024 Q1) and a trimmed GBPUSD were written in FirstRate format
  and imported with the real FX importer into scratch catalogs (`qa-fx-cross-full`, and
  `qa-fx-cross-late` where GBPUSD starts 2024-01-15) under a scratch `CATALOG_BASE_PATH`.
  `/srv/market-data` was only read. The import added `catalog_instruments` rows for those
  two scratch catalog names.
- **Dashboard**: T3's in-app browser cannot start on this host (missing system libraries:
  `libatk-1.0`, `libgbm`, `libasound`, ...; `sudo t3 browser setup` installs them), so pages
  were checked over HTTP. That covers the rendered HTML, the HTMX fragments, the JSON APIs the
  charts read, and a `POST /backtests/run` (HX request) for the Run form. JS rendering and
  visual layout were **not** checked in a real browser.

### Surfaces

- **CLI**: `EUR/USD`, `EUR.USD`, `gbp/usd`, `GBP.USD` and `USD/JPY` all resolve to the catalog
  ticker and `-MID` bars. `--units 100000` trades exactly 100,000. `--spread-pips 1.0` is

  above. The chart APIs (`/api/timeseries/run`: MID candles incl. synthetic EURGBP;
  `/api/equity`, `/api/trades`) return 200. A Run-form POST (`EUR.USD`, `firstrate-fx`,

## Bugs found and fixed

1. **Riptide hard stop covers only the first part of a split entry** (strategies repo, Major).
   Nautilus' bar matcher offers a quarter of a bar's volume at each OHLC point, and FX volume
   is a tick count, so most daily FX entries fill in parts (USDJPY 2023-07-10: 81,022 +
   18,978). `on_position_opened` sized the stop from the first part: 13 of 16 EURUSD and 8 of
   24 USDJPY stops (2015-2025) were short, and the 2023-07-13 USDJPY stop-out left 18,978
   units open, unprotected, until the next green candle. Fix: `on_position_changed` replaces
   a smaller stop with one for the whole position at the same trigger.
   Tests (red first): `test_riptide_stop.py::test_an_entry_filled_in_parts_is_fully_covered_by_the_stop`
   and `::test_a_stop_out_after_a_split_entry_closes_the_whole_position` (both fill models).
   Commits: strategies `a60dec8` (PR #5, stacked on #4); pin bump `be21b36`. riptide_fx USDJPY
   moves to -0.09% (USD 999,093.44); EURUSD and AAPL unchanged.
2. **Trade Statistics net profit drops "breakeven" trades** (pre-existing, made visible by
   FX). `calculate_trade_statistics` buckets P&L in (-10, 0] as breakeven and left it out of
   `net_profit`/`expectancy`, so the dashboard showed EURGBP -154.17 for trades summing to
   -156.89. FX trades often lose a few dollars to costs alone. Fix: sum every closed trade.
   Test (red first): `tests/unit/services/test_trade_analytics.py::TestTradeStatistics::test_net_profit_includes_breakeven_trades`.
   Commit `0ff29fb`. The bucket counts and total profit/loss are unchanged.

## Not fixed (and why)

- **`backtest reproduce` ignores the run's named catalog** (pre-existing, not FX). Reproducing
  a `catalog:firstrate-futures` ES run fell through to an IBKR fetch, which failed to connect.
  Reproducing an AAPL `firstrate-stocks` run failed on "bar.open.precision=4 did not match
  instrument precision 2" (`101b2731`). Outside the FX stack, and it touches the IBKR path;
  for Allay to schedule.
- **FX "Net P&L (USD)" excludes open positions** (CLI `show`, MCP `fx.net_pnl_usd`, dashboard
  panel): closed trades only, so it differs from the balance change by an open trade's entry
  costs (EURUSD -3,170.31 vs -3,174.61). The dashboard subtitle says "Closed trades"; the CLI
  and MCP labels do not. Wording question (Q5), not a calculation error.
- **MCP cannot set `units`** (or futures `contracts`): `SMAParameters` lists neither, so
  `submit_backtest(params={"units": ...})` is refused. The model is shared with the live path
  (guard lists), and the M5 MCP contract did not promise it. Q2.
- **Cosmetic**: `--symbol EUR/GBP` on a catalog without it says "Ticker 'EUR/GBP' not found"
  (not normalised) and suggests `ntrader data import-csv` (FX uses
  `import --format firstrate --asset-class fx`). The no-data case adds a generic "IBKR
  connection unavailable" panel under the precise message (pre-existing, all catalogs).
- **Stored `profit_pct` is not side-aware** (pre-existing, documented in M5): a profitable
  short exports `profit_pct -0.5165` next to `return_on_underlying_pct 0.5165`.
- **Margin-gate items open on #63**: not re-tested beyond what the runs exercised (no order was
  denied in any QA run; peak leverage 1.0x on buy_and_hold).

   says "typically under 0.1%" for 1-hour bars). Accept for daily FX, or close the lag?
